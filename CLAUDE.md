# CLAUDE.md

## Project Overview

Streamlit application for structured extraction, document understanding, and template generation with NuMind NuExtract on Apple Silicon with MLX. Uses `numind/NuExtract3-mlx-8bits` (a 4B-parameter Qwen3-family vision-language model) via [mlx-vlm](https://github.com/Blaizzy/mlx-vlm). Mirrors the official [NuExtract3 HF Space](https://huggingface.co/spaces/numind/NuExtract3) architecture but uses local MLX inference instead of remote vLLM.

Three modes: structured JSON extraction (typed template + image/text → JSON), document-to-markdown (image → Markdown), and template generation (NL description → JSON template). Streaming output with optional `<think>...</think>` reasoning trace.

## Commands

```bash
uv sync                                       # Setup environment
git config core.hooksPath .githooks           # One-time per clone: enable the pre-push gates
uv run streamlit run streamlit_app.py         # Run the app
uv run --frozen ruff check .                  # Lint (CI gate)
uv run --frozen ruff format --check .         # Format check (CI gate); drop --check to rewrite
uv run --frozen ty check                      # Type check (CI gate)
uv run --frozen pytest                        # Tests (CI gate)
uv run --frozen pytest tests/test_nuextract.py::test_name   # Run a single test
uv lock && uv sync                            # After editing [project.dependencies]
uv run python scripts/probe_mlx_vlm.py        # Model probe — ~5 GB download, preconditions below
```

**Always `--frozen` for the gates.** A bare `uv run` locks and syncs by default, silently rewriting an out-of-date `uv.lock` in the working tree; see the pre-push section for why that reddens `main`.

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff. For anything touching Streamlit, invoke `developing-with-streamlit` — it loads docs matched to the installed version, which matters here (see the Streamlit pin in Key Details).

CI via GitHub Actions (`.github/workflows/ci.yml`): lint, format check, type check, and `pytest` gate **every branch push** (`branches: ["**"]`), pull requests, and `workflow_dispatch`; a `release` job runs after them (below). Runs on `macos-15` (Apple Silicon) for MLX compatibility — **not `macos-14`**, which GitHub retires on 2026-11-02 ([actions/runner-images#13518](https://github.com/actions/runner-images/issues/13518)); `macos-26`/`macos-latest` is the next step up, but that image has an open Metal-toolchain gap worth checking first, since MLX is Metal. The unfiltered `pull_request` trigger exists for **fork** PRs — a push inside a fork does not trigger this repo's workflows — and is safe precisely because it is `pull_request` (read-only token, no secrets) and never `pull_request_target`. Its one cost: a *same-repo* branch with an open PR runs twice, once per event.

**Token scope is two-tier.** Workflow-level `permissions: contents: read` keeps the `test` job — which runs fork-PR code — from inheriting a widened repo default; `contents: write` is re-granted only on the `release` job. Drop the job-level grant and `gh release create` fails; drop the workflow-level one and the token silently widens for fork PRs.

**`timeout-minutes: 15` is load-bearing, not hygiene.** Without it a hung step burns GitHub's 360-minute default — which has already happened twice, both runs cancelled at exactly 6h inside `Run tests` (IDs in `ci.yml`). A timeout lands as `cancelled`, not `failure`, so **no failure notification fires** and the next green push quietly paints over it. The repo is public, so the runners are free: nothing bills you into noticing.

**There is no *workflow-level* `concurrency` block; the `release` job carries its own.** The removed workflow-level one keyed `main` on `github.run_id` — unique per run, so the group always held exactly one member by construction and could never dedupe anything. Since `15b8480` enabled branch CI, restoring it is a live trade-off: superseding stale branch runs would save wall-clock, against which these runners are free here and redundant runs cost only noise. If you do restore it, copy the expression exactly:

```yaml
group: ${{ github.workflow }}-${{ github.ref == 'refs/heads/main' && github.run_id || github.ref }}
cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}
```

The `run_id` ternary is not optional — GitHub unconditionally cancels an already-*pending* run in a group when a new one queues, so a group keyed on plain `github.ref` would kill queued `main` runs, and it would do so silently (a cancel raises no failure notification, per the paragraph above). Note also that `concurrency` can never dedupe a `push` run against a `pull_request` run for the same commit: those land in different groups.

**Nearly everything CI depends on is pinned**, so a green build rarely turns red without a repo change: Python deps via `==` + `uv sync --locked`, the interpreter via `.python-version` (3.13), uv itself via setup-uv's `version:` input, and setup-uv by exact tag. **`--locked`, not `--frozen`** — `--frozen` installs whatever `uv.lock` says and never checks it against `pyproject.toml`, so a dependency edit that was never relocked passes CI green while testing the *old* pins; `--locked` asserts the two agree and fails if they don't. Three inputs still float: `actions/checkout@v7` is a moving major tag (setup-uv cannot do the same — it stopped publishing moving majors after `v7`, hence the exact `@v10.0.1`), the `release` job's `ubuntu-latest` is a moving image alias (it needs no Apple Silicon — it only calls the GitHub API), and `macos-15` is on a deprecation clock.

**Releases are automated inside `ci.yml`; there is no `release.yml`** (it was deleted). A `release` job with `needs: test` runs only on a `push` to `main`, reads `[project].version` from `pyproject.toml`, and if no `v<version>` tag exists yet creates the tag *and* the GitHub Release in a single `gh release create --target <sha>` call. The whole procedure is therefore **bump the version, commit, push** — no `git tag` step, because the tag is derived *from* the version rather than checked against it. Four non-obvious constraints shape this:

- **A tag-triggered workflow cannot be part of the chain.** Per GitHub, *"events triggered by the `GITHUB_TOKEN` will not create a new workflow run"* — so a tag pushed by CI fires nothing and `on: push: tags:` is dead on arrival. The suppression covers **event delivery only**; the Releases *API* works fine with `GITHUB_TOKEN`, which is why one `gh release create` both tags and releases and nothing ever `git push`es a tag. `needs: test` is consequently the only thing that actually guarantees the four gates ran on the released commit.
- **Bump detection asks "does tag `v<version>` already exist?", never a `github.event.before..github.sha` diff.** A state question is idempotent: re-running the workflow, force-pushing, or pushing ten commits at once each still produce exactly one release. A diff question breaks in all three.
- **Notes come from the commit log, not `--generate-notes`.** GitHub builds auto-notes by summarising merged pull requests; this repo releases straight from `main` and has never had one, so `--generate-notes` would emit little more than a compare link. The job writes `git log <prev-tag>..HEAD` to a file and passes `--notes-file`, which also keeps commit subjects out of the shell. The baseline is `git describe --match 'v[0-9]*'`, not a bare `git describe` — an unrelated tag would otherwise become the baseline and silently truncate the range. The prerelease test is `case "$VERSION" in *[!0-9.]*)` — any version containing a character other than digits and dots (`1.3.0rc1`, `1.3.0.dev1`) ships `--prerelease` so it cannot take the Latest badge; a digits-and-dots version always ships as a full release.
- **The job needs its own `concurrency` group** (`release-${{ github.ref }}`, `cancel-in-progress: false`). It is check-then-act — *does `v<version>` exist?* then *create it* — so two pushes landing inside that window would both decide to release, and the loser dies on "release already exists", reddening `main`.

The `v1.2.0` release was created by hand and predates all of this — and since `pyproject.toml` is still at `1.2.0`, the release job has only ever taken its skip path. **The `gh release create` step has never executed in CI**; watch the first version bump closely.

**Workflow: local `type/kebab-summary` branch → `--no-ff` merge into `main` → push. There are no PRs.** Commit subjects are Conventional Commits (`ci:`/`feat:`/`fix:`/`chore:`/`docs:`/`test:`/`refactor:` + lowercase summary) — not a style preference: the release job pastes non-merge subjects verbatim into the public GitHub Release body, so a sloppy subject ships. Keep the merge commit (`--no-ff`); `--no-merges` excludes it from the notes, so it records the branch without adding noise.

Lint/type config lives in `pyproject.toml`: Ruff selects `E`/`F`/`I` (import sort)/`UP` (pyupgrade), with line length deferred to the formatter (`ignore = ["E501"]`); ty targets the `requires-python` floor (3.12) with `error-on-warning`. **The runtime/type-check version split is deliberate** — code runs on 3.13 (`.python-version`) while ty analyzes against the 3.12 floor, so `requires-python = ">=3.12"` stays honest without holding the runtime back.

Conventions ruff does **not** enforce, so new code has to carry them by hand: app and script modules open with a module docstring then `from __future__ import annotations` (test modules do neither); every function has a docstring; functions go keyword-only after the leading positionals (`def f(a, *, b, c)`); module-private helpers are `_`-prefixed; and any non-obvious decision carries a comment saying *why*, not what.

Team-shared Claude Code config in `.claude/` (tracked in git) enforces these same gates at edit-time, via **one** hook plus declarative permissions. Note that `.gitignore` excludes the *contents* of `.claude/` and `docs/` and re-includes by exception (`!.claude/settings.json`, `!.claude/hooks/`, `!docs/*.png`) — git cannot re-include a file whose parent directory is excluded, so anything new you add there (a `.claude/agents/…`, a non-PNG doc) is silently untracked until you add a matching `!` negation.

- **`.claude/hooks/py-checks.sh`** (PostToolUse) — after each `.py` edit: `ruff check --fix` → `ruff format` → **`ruff check`** → `ty check`. **Lint-fix before format is Astral's recommended order** — fixes rewrite code structure (`I` re-sorts imports, `UP` rewrites syntax), so formatting last guarantees formatted output whatever the fixer did. **Lint is checked twice on purpose** — the reported verdict must come from a pass over the *final* bytes, since the first two steps mutate the file; reporting step 1's output would give line numbers pointing into the pre-format file and could exit 0 on a lint-dirty result. These four calls are bare `uv run`, not `--frozen`, so a `.py` edit made while `uv.lock` is stale **relocks it in the working tree** — which then lets pre-push's `uv lock --check` pass over a stale *committed* lock. Commit `uv.lock` alongside any `pyproject.toml` change. Needs `jq` + `uv`; missing `jq` degrades to a silent no-op.
- **`permissions.deny` in `.claude/settings.json`** — denies `Read` *and* `Edit` on `.env*` and `.streamlit/secrets.toml`. Replaced a `PreToolUse` hook; broader on **tool coverage**, since permission rules sit above tool dispatch and so also block **reads**, which a matcher scoped to `Write|Edit|MultiEdit` never did. Four things in that list look like redundancy and are not — **read `.claude/hooks/README.md` before "simplifying" any of them**:
  - Each path is listed **twice**, `/…` and `**/…`: `/.env*` anchors at the project root, `**/.env*` matches at any depth under the cwd. (The `./.env` form in Claude Code's own docs anchors to `<cwd>` alone and misses the project's `.env` from a subdirectory.)
  - **`.env*`, not `.env` + `.env.*`** — one glob also covers `.envrc`, a common `HF_TOKEN` home. `.gitignore` uses `.env*` for the same reason, so the two lists stay in sync.
  - The **`.[eE][nN][vV]*` duplicates** restore case-insensitive coverage of `.ENV` on macOS; the plain rules stay alongside so the class rules can only add coverage, never silently replace it.
  - **No `Write(...)` rule, deliberately** — file permissions are checked against `Edit(path)`/`Read(path)` only; a `Write`/`MultiEdit`/`NotebookEdit` rule is accepted, never consulted, and warns at startup. `Edit` covers every built-in editing tool, and `Read` is listed alongside it because a `Read` deny does not cover `NotebookEdit`.

  **Accident guardrail, not a security boundary — and the bypass is live here.** Deny rules do not reach arbitrary subprocesses, and `.claude/settings.local.json` allowlists `Bash(uv run *)`, so `uv run python -c "print(open('.env').read())"` prints `HF_TOKEN` into context with no rule firing. They stop the accident, not a determined path.

**Tests are not a Claude Code hook — they are a git hook.** A `Stop` hook that ran `pytest` was removed: it cost ~9s per turn and keyed on working-tree state, so any dirty `.py` file made it fire on every turn, including pure-conversation ones. Its job moved to `.githooks/pre-push` — the right granularity (once per *push*, not per turn), and it protects a hand-typed `git push`, which no agent hook can. It runs **`uv lock --check` plus all four CI gates**, cheapest first (`uv lock --check` → `ruff check` → `ruff format --check` → `ty check` → `pytest`), aborting at the first failure: gating on `pytest` alone would let a lint or type error push cleanly onto `main` and turn CI red there. It deliberately uses no `--fix` and no bare `ruff format` — a hook that rewrites the tree mid-push would make the tested tree differ from the reviewed one.

**`uv lock --check` runs first, and every gate runs under `uv run --frozen`, for one reason:** `uv run` locks and syncs by default, so a bare `uv run` silently *rewrites* an out-of-date `uv.lock` in the working tree. Every gate would then pass against the regenerated lock while the committed lock stayed stale, the push would succeed, and CI's `uv sync --locked` would fail on `main` — the precise failure this hook exists to stop. It is **opt-in per clone**, since git does not share hooks: `git config core.hooksPath .githooks`. The hook skips deletion-only pushes, warns when the tree has uncommitted *or untracked* changes (it tests the tree, not the pushed commits — and `git diff` alone is blind to untracked files that pytest still collects), and is bypassed with `git push --no-verify`.

Hooks are snapshotted at session start, so restart after pulling changes. Details in `.claude/hooks/README.md`; personal overrides go in the gitignored `.claude/settings.local.json`.

## Architecture

App in `streamlit_app.py`, runtime wrapper in `nuextract.py`, probe in `scripts/probe_mlx_vlm.py`.

### `nuextract.py`

Thin wrapper around mlx-vlm. Module-level imports of `huggingface_hub.snapshot_download`, `mlx_vlm.load as mlx_vlm_load`, `mlx_vlm.stream_generate as mlx_vlm_stream_generate` — so tests patch `nuextract.snapshot_download` / `nuextract.mlx_vlm_load` / `nuextract.mlx_vlm_stream_generate` (standard "patch where used" pattern). The aliases are the patch targets; `nuextract.load`/`nuextract.stream_generate` do not exist.

- **Constants** — `DEFAULT_MODEL_ID = "numind/NuExtract3-mlx-8bits"`, `DEFAULT_MAX_TOKENS = 4096`, `DEFAULT_TEMPERATURE = 0.0`, `MODE_STRUCTURED = "structured"`, `MODE_CONTENT = "content"`, `MODE_MARKDOWN = "markdown"`, `MODE_TEMPLATE_GENERATION = "template-generation"`.
  **`MODE_STRUCTURED`/`MODE_CONTENT` are value-asserted by tests but intentionally never passed by the app.** Structured extraction sends `template=...` with `mode=None` (the Jinja infers `structured` from the template), and `_run_mode` detects exactly that: `is_structured = template is not None and mode is None`. Passing `MODE_STRUCTURED` explicitly to "tidy up" the extract handler flips `is_structured` to False and silently downgrades the Result pane from a JSON code block to plain markdown — **with all 103 tests still green**. Deleting the two "unused" constants breaks `test_nuextract.py`.
- **`patch_processor_config(local_dir)`** — Patches the MLX repo's `processor_config.json` packaging bug (see Key Details). Idempotent, returns `True` if changed.
- **`load_model(model_id)`** — `snapshot_download` → `patch_processor_config` → `mlx_vlm.load`. Returns `(model, processor)`.
- **`build_messages(text, image_path, system_prompt)`** — Builds a chat message list: optional `{"role": "system", "content": ...}` first (string-only — the Jinja raises if it contains images), then a `{"role": "user", "content": [...]}` with `{"type": "image", "image": path}` and/or `{"type": "text", "text": ...}` parts. The Jinja template inserts the vision placeholder; actual pixel data flows separately via `stream_generate(image=...)`.
- **`render_prompt(processor, messages, *, template, instructions, mode, enable_thinking)`** — Calls `processor.apply_chat_template(...)` with task kwargs **inline** (HF transformers convention), NOT nested under `chat_template_kwargs` (that's a vLLM-specific convention). Omits `None`/empty values so the template's defaults apply.
- **`stream_extract(model, processor, *, text, image_path, system_prompt, template, instructions, mode, enable_thinking, temperature, max_tokens)`** — Builds messages → renders prompt → calls `mlx_vlm.stream_generate`. Yields **cumulative** text on each chunk (not per-chunk deltas) for direct rendering into a Streamlit placeholder.
- **`split_reasoning_and_output(text, reasoning_enabled)`** — Splits on `</think>` (case-insensitive). Returns `("", text)` when reasoning is off; returns `(text, "")` when reasoning is on but `</think>` hasn't arrived yet.
- **`extract_answer_block(text)`** — Pulls `<answer>...</answer>` contents if present, else the longest span at any `{` position that parses via `json.JSONDecoder.raw_decode`, else the stripped text. Correctly handles the "reasoning text + JSON" case without merging unrelated spans.
- **`pretty_json_or_text(text)`** — Tries `json.loads` + indented re-dump; falls back to the original on parse failure.

### `streamlit_app.py`

Two-column layout. Left: inputs. Right: action buttons + outputs (wrapped in an `st.fragment`).

- **`get_model()`** — `@st.cache_resource` wrapper around `nuextract.load_model`. **It returns the exception rather than raising it, so a *failed* load is cached too.** `st.cache_resource` writes an entry only when the function returns (`cache_utils.py`'s `_handle_cache_miss` reaches `write_result` only on the success path), so a raising load is a fresh cache miss on every rerun. That was harmless while the load blocked the whole page — nothing had rendered, so nothing could trigger a rerun — but the input widgets now paint first and stay live through a failure, which would turn every slider drag into another download attempt. The call site branches on `isinstance(loaded, Exception)` and offers an explicit **Retry model load** button that calls `get_model.clear()`; making retry a deliberate click is the entire point, so do not "simplify" this back to a bare `return load_model()`. The failure renders in three parts, and the split is deliberate: a one-line `st.error` headline naming the exception type, the message through `st.code` because `st.error`'s body is GitHub-flavored Markdown with soft breaks disabled and this path's real failures (an offline hub download, an unpatched `processor_config.json`) are multi-line, and the traceback inside a collapsed `st.expander` — since `get_model` returns the exception instead of raising it, Streamlit never reports it and nothing logs it, so `st.exception(loaded)` is the only place the frame that names the cause survives. That whole branch still has no test; `key="retry_model_load_button"` exists to make covering it possible.
- **`_save_uploaded_image(uploaded_file)`** — Persists `st.file_uploader` bytes to a temp file once per upload, keyed on `uploaded_file.file_id` in `st.session_state`. Reruns return the cached path; a new upload deletes the previous temp file before writing the new one, and removing the upload deletes the orphaned temp file and clears the cached `session_state` keys. Required because mlx-vlm wants file paths/URLs.
- **`_validate_template(template_str)`** — Validates JSON template is a non-empty dict; returns `(parsed, error)`.
- **`_render_output_pane(output_placeholder, reasoning_placeholder, accumulated, *, reasoning_enabled, is_structured, final=False)`** — Updates both panes from a single stream chunk: routes reasoning trace to its placeholder (or shows `_(reasoning disabled)_` when off), then renders output as JSON code-block (structured/template-gen modes) or markdown (markdown mode). Shows `_(waiting for output after </think>)_` placeholder while reasoning is in progress. Two details are load-bearing:
  - **`final` gates `extract_answer_block` + `pretty_json_or_text` to the one post-stream call.** Those helpers have a *whole-document* contract — `extract_answer_block` returns the longest span that **parses** — which every intermediate chunk violates: mid-stream the outer object is still truncated, so the longest parsing span is whichever *nested* object closed first. Running them per chunk (as the code did until `final` existed) makes the Result pane grow normally, then visibly **shrink** to a nested sub-object and sit frozen there until the last token, when it snaps to the full document. Reproduce with `extract_answer_block(full_json[:85%])`. `_run_mode` therefore streams the raw partial and calls back once with `final=True`, placed **after** the empty-output guard — above it, an empty run repaints `_(generating...)_` over its own warning — and **gated on `render_as_json`**, since for markdown mode the final render is byte-identical to the last streaming one and would re-send the largest document the app produces. Regression tests: `test_render_output_pane_streaming_partial_json_is_not_collapsed`, `..._final_extracts_answer_and_pretty_prints`, and `test_completed_run_strips_answer_wrapper_and_pretty_prints` — the last one is the only cover for the **call site**, and it asserts the exact indented body (`'{\n  "k": 1\n}'`) precisely because a substring assertion passes whether or not the final pass ran at all.
  - **The streaming branch renders unconditionally as `st.code(..., language="json", wrap_lines=True)` and never inspects the partial.** An earlier revision prefix-tested `("{", "[", "<answer>")` to pick code-vs-markdown; that is the wrong shape and was reverted. Any preamble (`Here is the extraction:\n{...}`), an `<ANSWER>` wrapper in the wrong case (`_ANSWER_RE` is `IGNORECASE`, a literal prefix test is not), or a stray `<think>` when reasoning is off routes the whole run's JSON through the Markdown renderer — the same untrusted-output-into-Markdown class as the reasoning-pane fence below. Structured mode is *asking* for JSON, so it renders as JSON and only the final pass — whose input `extract_answer_block` has already cleaned — decides prose-vs-JSON. `wrap_lines=True` matters more here than it looks: the streamed partial is the model's raw output, so compact JSON would otherwise be one long horizontally-scrolling line whose visible portion stops changing.
  - **The reasoning trace goes through `st.code(think, language=None, wrap_lines=True, height=300)`, never a hand-built ` ```text ` fence.** The `height` is what makes the pane scroll rather than grow: the Result pane and its download button sit *below* it, so an uncapped trace pushes them off-screen for the whole run. `think` is untrusted model output; a fence *inside* it closes the wrapper and hands the remainder to the Markdown renderer (headings render, tables render, ` ```mermaid ` renders as a diagram). Markdown-mode reasoning quotes fences routinely, so this fires in normal use. `language=None` — not `"text"` — is the documented spelling for plain monospace. Regression test: `test_reasoning_trace_containing_a_code_fence_stays_in_one_element`.
- **`_download_payload(accumulated, *, download_kind, reasoning)`** — Splits off the reasoning trace, then applies `extract_answer_block` when `_DOWNLOAD_CONFIGS[download_kind]`'s 4th field says the mode is JSON. Returns the exact text a download would write. **It is also the only honest emptiness test, and `_run_mode`'s completion guard uses it for exactly that reason.** Guarding on `accumulated` — as the code did originally — passes two runs that produced no answer whatsoever, because the raw text still carries the trace and the wrapper: (1) reasoning on with the token budget spent before `</think>` ever arrives, which ended the run showing the *mid-stream* `_(waiting for output after </think>)_` caption as its terminal state, and (2) a closed but empty `<answer></answer>`, which blanked the Result pane at the final render. Both then rendered a download button whose payload was `""`. Regression tests: `test_reasoning_that_never_closes_warns_instead_of_stalling`, `test_empty_answer_wrapper_warns_instead_of_blanking_the_pane`. Case (1) gets its own warning naming Max tokens and the Reasoning toggle, since unlike a genuinely empty response it has a remedy the user can reach.
- **`_render_download_button(placeholder, payload, *, download_kind)`** — Renders a `st.download_button` for an **already-cleaned** payload, with `on_click="ignore"` so downloading stays client-side and doesn't rerun the fragment (a rerun would repaint the idle hint over the result and drop the button). `download_kind` selects label, filename and mime. It deliberately does **not** clean the text itself any more: `_run_mode` needs the payload before this call in order to guard on it, and deriving it twice is how the guard and the button drift apart.
- **`_run_mode(...)`** — Drives one streamed generation: calls `_render_output_pane` on every chunk yielded by `stream_extract`, then re-renders once with `final=True` and fills the download placeholder on completion. `render_as_json = is_structured or mode == MODE_TEMPLATE_GENERATION` is computed once and passed to both calls; letting the two drift is how the final render silently disagrees with the streaming one. On the success path it also stores the run under `_LAST_RUN_KEY` in `session_state` (`accumulated`, `payload`, `download_kind`, `reasoning`, `render_as_json`) for `_output_section` to replay — **below** the empty-payload guard, so a run that produced no answer can never come back as a replayable result, and carrying `payload` rather than re-deriving it for the same reason `_render_download_button` does not clean its own text.
- **`_output_section()`** — `@st.fragment`-decorated, **takes no arguments**. Renders the three action buttons (Extract / Markdown / Template-gen) in a horizontal container, plus the always-rendered Reasoning + Result placeholders and the download placeholder (the Result pane shows an idle empty-state hint until a run produces output), **then calls `get_model()` itself**, then runs the button handlers. Loading inside the fragment rather than accepting a loaded pair is what lets the ~5 GB download sit below this section's own chrome: nothing on the page waits on it except the Result slot the output lands in, which shows the spinner. Reverting to `_output_section(model, processor)` necessarily moves the load back above the buttons and is caught by `test_model_loads_after_the_page_chrome_renders`. Lives in a fragment so clicking a generate button reruns **only** this region — the left-column input widgets keep their state and aren't re-rendered during generation. The buttons must be inside the fragment for that isolation to apply (a fragment only reruns independently when the triggering widget is inside it). Reads input values from `st.session_state` by widget key (the left-column widgets populate them on the full rerun that precedes the fragment). Handlers validate inputs (markdown requires image; extract requires template + either image or text) and call `_run_mode`. **When no button fired it replays `_LAST_RUN_KEY` instead of painting the idle hint**, because the left-column widgets sit outside the fragment: touching any of them is a *full* rerun that re-creates all three placeholders empty with no button pressed, which used to discard a finished result and its download button. The replay calls `_render_output_pane(..., final=True)` for every mode — including markdown, where `_run_mode` skips the final pass only because there it duplicates the last streaming render, which is not true of a placeholder just re-created empty. Regression test: `test_completed_run_survives_a_left_column_edit`, verified failing with the lookup stubbed to `None`.
- **Top-level UI** — `st.set_page_config(page_icon=":material/document_scanner:", layout="wide")`, title, then `st.columns([1, 1])` for the two panes. **The model-load spinner sits inside `col_right`, below the whole left column, and the ordering is load-bearing.** Streamlit emits a UI delta per `st.*` call, so a blocking call placed above the columns (where it used to be) stops *every* input widget from painting until the ~5 GB download finishes — the app renders a title and a spinner and nothing else. Loading after the left column means only the pane that actually needs the model waits. Keep `st.spinner` rather than `st.skeleton` here: the "~5 GB" text is what stops a multi-minute wait from reading as a hang. This is the ordering rule in `references/performance.md` ("Render stable UI before slow work") — which ships **inside the installed `streamlit` package** (`.venv/…/streamlit/.agents/skills/developing-with-streamlit/references/`) and **not in this repo**, so grepping for it locally finds nothing; reach it via the `developing-with-streamlit` skill.

  `test_model_loads_after_the_page_chrome_renders` gates the ordering. Render order is not observable from `AppTest`, so it asserts *structurally*: keyed widgets register themselves in `session_state` as they render, so an anchor key is present when `load_model` is called iff that widget already ran. **It checks two anchors, each the last keyed widget of its group, and "last" is load-bearing in both cases** — an anchor further up still passes with the load sitting inside the group it is meant to guard. `reasoning_checkbox` is the last of `col_left`'s 7 inputs (`template_input`, the 3rd, would permit a *mid-column* load); `template_button` is the last of the three action buttons (guarding the fragment's own chrome). Verified failing in all three directions: a load above `st.columns`, a mid-column load, and a load above the buttons. It also asserts `not at.exception` first, since a crash before either anchor would otherwise fail an ordering assertion and blame the wrong file. The `cold_model_cache` fixture clears `st.cache_resource` on both sides — `get_model` is cached process-wide, so without the pre-clear an earlier test's entry means the stub never runs and the assertion silently observes nothing, and without the post-clear the suite's cache keeps a pair built by a stub `monkeypatch` has already removed. Left pane: image uploader (capped at `_MAX_IMAGE_UPLOAD_MB` = 25 via `max_upload_size`, since `getvalue()` reads the whole file into the same unified memory as a ~5 GB model; preview bounded by `st.container(height=320)` because `st.image` has no height parameter and an unbounded portrait scan pushes every control below it off-screen), optional text area, JSON template editor (`DEFAULT_TEMPLATE`), optional instructions, temperature + max-tokens sliders and a reasoning toggle on its own row (keyed `reasoning_checkbox` still, so this anchor is unchanged) — all keyed, return values unused (read via `session_state` in the fragment). Right pane: `Output` subheader then `_output_section()`.

**Adding a mode or a control.** A new mode touches five places: a `MODE_*` constant in `nuextract.py`; a `_DOWNLOAD_CONFIGS` entry (label, filename, mime, whether `extract_answer_block` strips wrappers); a keyed `st.button` inside `_output_section`'s horizontal container; an `elif` handler that validates inputs and calls `_run_mode`; and tests in all three files — then update the counts here *and* in README. A new input control must be a **keyed** left-column widget whose return value is discarded and re-read as `st.session_state.get("<key>", <default>)` inside the fragment: a value captured at the widget call site is stale during a fragment-only rerun, because the left column does not re-execute. That is the whole reason for the keyed-widget pattern.

Changing the pane layout or any visible control invalidates `docs/screenshot-dark.png`, the single image README embeds (the light-theme companion was removed). **Bumping the `streamlit` pin invalidates it too** — since the theme config was deleted, the entire look (colours, radii, borders, code font) now comes from the pinned version's built-in themes rather than from anything in this repo, so a dependency upgrade can repaint the app with no diff to point at. Regenerating means a real model load, and there is **no repo-level lever to force dark mode** any more: pick Dark in the app's Settings menu, or flip the OS/browser `prefers-color-scheme`. Flag it for the user rather than shipping a stale image. The committed image has Streamlit's dev toolbar (the **Deploy** button and kebab menu) cropped off the top — it advertises a hosted-deploy path this Apple-Silicon-only app does not offer. Keep that crop on any re-shoot, or suppress the toolbar at the source with `client.toolbarMode = "minimal"` (which means a `.streamlit/config.toml` holding only that key — harmless, since it sets no `[theme]`).

### `scripts/probe_mlx_vlm.py`

Standalone probe for the mlx-vlm/transformers stack. **It calls `mlx_vlm.load()` directly, so it does *not* apply `patch_processor_config`** — against an unpatched cache, check 1 downloads ~5 GB and *then* dies with `ValueError: Unrecognized image processor` (the MLX repo's `Qwen3VLImageProcessor` bug, see Key Details), exiting before checks 2-6 and with a traceback that never names the cause. Run `nuextract.load_model()` or the app once first. Six checks:
1. `mlx_vlm.load()` succeeds on `numind/NuExtract3-mlx-8bits`
2. `processor.apply_chat_template(template=..., enable_thinking=False)` produces a rendered prompt with the typed template embedded under `【template_start】`
3. `mode='markdown'` reassigns to `【task】content` (per the model Jinja's mode-collapsing logic)
4. `mode='template-generation'` produces `【task】template generation`
5. End-to-end `mlx_vlm.generate()` returns parseable JSON for a trivial extraction
6. End-to-end `mlx_vlm.generate(image=[...])` on a PIL-rendered PNG returns typed JSON — the **only** coverage of the vision path (torchvision + the image processor), since every test in `tests/` mocks `mlx_vlm.stream_generate`. The image is generated at run time, so no binary fixture is committed.

Run: `uv run python scripts/probe_mlx_vlm.py`. Exits non-zero on any failure.

## Key Details

- **Model**: `numind/NuExtract3-mlx-8bits` — 8-bit affine quant of NuExtract3 (Qwen3.5 4B base), ~5 GB on disk
- **Context**: 262K tokens declared by the model (`text_config.max_position_embeddings = 262144`), but the practical limit is bounded by unified memory + KV cache size
- **Pinned transformers**: `==5.15.0`. The floor is **not freely chosen** — `mlx-vlm==0.6.13` declares `transformers>=5.14.0`, so transformers cannot be rolled back without also downgrading mlx-vlm. (The model's own declared `transformers_version` is `5.5.4`, but `qwen3_5` only enters the auto-resolver mapping in much later versions.) Two invariants make the stack work — `qwen3_5` in `CONFIG_MAPPING_NAMES` and `Qwen2VLImageProcessor` still exported — and both are asserted by model-free tests in `tests/test_nuextract.py`, so CI gates them rather than a checklist.
- **Required torchvision**: as of transformers 5.15 the image-processor mapping is backend-keyed — `qwen3_5 → {"torchvision": "Qwen2VLImageProcessor", "pil": "Qwen2VLImageProcessorPil"}` — so the image processor alone no longer forces torchvision. The hard requirement now comes from `Qwen3VLVideoProcessor`, which the processor constructs eagerly on load and which requires **torchvision itself, not merely torch**: with torchvision absent the auto-mapping entry is nulled and `AutoProcessor.from_pretrained` dies on `Qwen3VLVideoProcessor requires the Torchvision library`. So swapping the `torchvision` pin for a direct `torch` pin breaks model load — and **CI would not catch it**, since every test mocks mlx-vlm and nothing in the suite builds a real processor. (torchvision is also the only thing pulling `torch` into the tree.)
- **Pinned Streamlit**: `==1.61.1`. The app uses APIs newer than most training data — `st.space("medium")`, `st.container(horizontal=True)`, `width="stretch"` (which supersedes the older `use_container_width`), `on_click="ignore"` on `st.download_button`, and `:material/…` icon strings. **Do not "modernise" these back to older spellings** — that is a regression, not a fix, and it is the highest-probability wrong edit in this repo. Invoke the `developing-with-streamlit` skill for any Streamlit change; it loads docs matched to the installed version.
- **Packaging-bug shim** in `nuextract.patch_processor_config()`: `numind/NuExtract3-mlx-8bits` declares `Qwen3VLImageProcessor`; the model author's own `numind/NuExtract3` declares `Qwen2VLImageProcessor` with otherwise identical geometry. **Upstream is authoritative, so this is a conversion bug in the MLX repo, not a workaround for a class missing from transformers.** Do not gate the shim on `hasattr(transformers, "Qwen3VLImageProcessor")` — the class being absent today is why the bug is *visible* (load fails loudly), not why the rewrite is *correct*; such a gate would silently stop patching the day transformers ships the class. The shim patches the locally cached copy on every `load_model()` call (idempotent).
- **Template kwarg API**: HF transformers' `apply_chat_template` accepts template variables as **direct keyword arguments** (e.g. `template="..."`, `mode="..."`, `enable_thinking=False`). The HF Space uses vLLM which expects them nested under `chat_template_kwargs={...}` — that convention does **not** apply to direct HF/mlx-vlm usage. As of transformers 5.15 this is conditional on the model's template, not universal: `apply_chat_template` introspects the Jinja for declared variables and routes anything undeclared into `processor_kwargs`, warning as it does. NuExtract3's template declares all four kwargs `render_prompt` sends, so nothing warns today — but a template change (or a stricter transformers) could turn this into a silent no-op, and the warning is the signal to watch for.
- **Unexercised transitive paths**: the dependency set carries `pandas` 3.x (Streamlit's dataframe/Altair rendering) and `opencv-python` 5.x (mlx-vlm's video path). Nothing in this app or its tests touches either, so both crossed a major version **unverified rather than verified** — a regression there would surface to a user, not to CI.
- **Modes** (from the model's `chat_template.jinja`, which ships inside the HF snapshot — **not in this repo**, so grepping for it locally finds nothing): setting `template=...` forces `mode='structured'`; `mode='markdown'` is reassigned to `'content'`; `mode='template-generation'` and `'document-detection'` are also valid. `enable_thinking=True` is only allowed for `structured` and `content` modes.
- **Output parsing**: NuExtract3 may emit `<answer>...</answer>` wrappers around structured output or raw JSON. `extract_answer_block` handles both.
- **Reasoning trace**: model emits `<think>...</think>` before the answer when `enable_thinking=True`. `split_reasoning_and_output` separates them for the two-pane UI.
- **Image input**: `st.file_uploader` (jpg/jpeg/png/webp), persisted to a temp file before passing to mlx-vlm. No clipboard support (Streamlit limitation vs the Gradio-based HF Space).
- **Theme**: none — the app ships **no `.streamlit/config.toml`**, so Streamlit's built-in Light and Dark themes apply and the Settings menu offers Light/Dark/System. **The initial theme is therefore the visitor's, not ours**: with no config, Streamlit resolves the default from `prefers-color-scheme`, which is why a single dark screenshot can misrepresent the app and why "run it in dark mode" has no repo-level switch behind it. This replaced a GitHub-inspired custom palette (colours plus `baseRadius`/`buttonRadius` 8px, `linkUnderline`, `showWidgetBorder`, `codeFont` — the shape/typography keys went with it, not just the palette). If you reintroduce a `[theme]` section, **it must define both `[theme.light]` and `[theme.dark]`**: a custom theme with only a bare `[theme]` table locks the app to one mode and removes the user's toggle. `.gitignore` ignores `.streamlit/secrets.toml` only, so a config.toml added back is tracked by default.
- **No PDF support** in v1 — matches the HF Space; users convert PDFs to images externally.
- **License**: project code is **MIT** (`LICENSE` at repo root — verbatim SPDX text so GitHub's detector recognizes it; also declared in `pyproject.toml` via PEP 639 `license = "MIT"` + `license-files = ["LICENSE"]`). The NuExtract3 model weights are separately **Apache-2.0** and downloaded at runtime (not redistributed by this repo), so the model license governs model usage, not this project's code. README has Acknowledgments + License sections crediting the upstream MIT HF Space.

## Tests

Total: 103 tests across three files. **No test loads a real model, and this is enforced rather than documented** — see the `tests/conftest.py` guard below. `HF_HOME=$(mktemp -d) HF_HUB_OFFLINE=1 uv run --frozen pytest` remains a useful independent cross-check but is *not* the enforcement mechanism: with a warm cache, offline mode succeeds, so on its own it passes locally and fails only on a cold CI runner. These are `pytest`-collected counts — parametrization expands `test_nuextract.py`'s `def test_` functions into 44 cases, so a raw `grep -c 'def test_'` undercounts.

**These counts are mirrored in `README.md`** (the Development block, the Project Structure tree, and Contributing) — add a test and three README spots go stale. README also independently restates the CI triggers, the release procedure, the `core.hooksPath` setup, the pinned `transformers` version, and the file tree; changing any of those here means the same edit there.

- **`tests/conftest.py`** — path setup, plus a session-scoped autouse fixture that replaces `nuextract.snapshot_download`, `nuextract.mlx_vlm_load` and `huggingface_hub.snapshot_download` with stand-ins that raise. A test that forgets to mock now fails in milliseconds with a message naming the fix, instead of pulling 4.8 GB. Tests that legitimately exercise those boundaries patch over the guard and restore it on exit, so it is safe always-on. Deliberately **narrow**: banning sockets outright would also catch this, but Streamlit gathers usage stats and AppTest runs the real script in-process, so a broad network ban risks failures unrelated to the bug being prevented. `test_nuextract.py::test_conftest_guard_blocks_a_forgotten_mock` is the regression test for the guard itself.

- **`tests/test_nuextract.py`** (44) — Pure function tests for the runtime wrapper. `extract_answer_block` and `pretty_json_or_text` cases are parametrized; integration boundaries (`load_model`, `stream_extract`) are tested by patching the `nuextract.*` namespace. Two tests import `transformers` directly to assert the compatibility invariants (see Key Details) — the only tests that touch a real dependency, and they load no model.
- **`tests/test_streamlit_app.py`** (28) — Helper function tests. The module-scoped `app` fixture mocks all Streamlit primitives so `streamlit_app` imports cleanly without a real model (`st.fragment` is patched to an identity decorator so the `_output_section` fragment body runs under the mocks). It enters them through a `contextlib.ExitStack` rather than one `with` statement: the 8 `_ST_NOOPS` are entered in a loop, and the 21 context managers sit **exactly at** CPython's statically-nested-block ceiling (measured on both 3.12 and 3.13: 21 compiles, a 22nd fails at *collection* with `SyntaxError: too many statically nested blocks`). Adding one more patch is what breaks a flat `with`, so keep the ExitStack. **It patches `nuextract.load_model` / `snapshot_download` / `mlx_vlm_load`, never `streamlit_app.load_model`**: `patch("streamlit_app.X")` resolves its target *by importing* `streamlit_app`, whose module body calls `get_model()`, so the real 4.8 GB download fires during patch setup — before the mock exists — and the fixture's subsequent `sys.modules.pop` + re-import rebinds `load_model` from `nuextract` and discards the mock anyway. Patch the dependency, not the consumer; the `conftest.py` guard now makes the mistake fail loudly rather than silently. `st.empty` is stubbed with `side_effect`, not `return_value`, because `_output_section` calls it three times (reasoning, output, download panes) and one shared mock would let output routed to the wrong pane still assert clean. Includes a regression test that removing an upload cleans up the orphaned temp file and session state.
- **`tests/test_streamlit_app_apptest.py`** (31) — End-to-end UI wiring via Streamlit's `AppTest`. The three model-loading stubs live in one `_stub_model_loading(monkeypatch, *, on_load=None)` helper shared by the `at` fixture and the ordering guard, so the set of stubbed boundaries is defined once — a second copy drifts, and a missed boundary fails as a 4.8 GB download rather than an obvious error. The `at_with_image` fixture drives a fake image into `st.file_uploader` via AppTest's native `set_value` API (added in Streamlit 1.56), exercising the real widget. Covers initial render (including the Result-pane empty-state hint rendered by the `_output_section` fragment and the model-load ordering guard described under Top-level UI), button validation, and streaming flow for text- and image-input paths (including the instructions field, template-gen system prompt, and template-gen reasoning override). `at.download_button` **is** exposed by AppTest (`streamlit/testing/v1/app_test.py`) and does surface the button rendered into the `st.empty()` placeholder — the file's decision not to assert it is a coverage gap, not a framework limit. AppTest's `DownloadButton` carries only `label`/`help`/`value`, so `file_name`/`mime`/payload assertions stay in `test_streamlit_app.py`.
